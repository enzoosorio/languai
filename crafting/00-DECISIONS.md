# 00 — Decisiones, Gaps y Preguntas abiertas

Documento canónico de **estado de criterio** del proyecto. Complementa a los specs temáticos (`ARCHITECTURE.md`, `FEEDBACK.md`, etc.): allí está el *qué*, aquí está el *por qué*, el *qué falta* y el *qué no sabemos*.

**Reglas de mantenimiento:**

- Las decisiones **no se editan**: se **superseden** con una nueva fila (`⛔ Superseded por Dn`). La numeración es estable y sin saltos.
- Cada decisión lleva cuatro campos obligatorios: decisión · por qué · alternativas descartadas · fecha. Sin el porqué no es una decisión.
- Cuando existe una **condición de caducidad comprobable**, va dentro de la celda de Estado.
- Un **gap** es un agujero conocido del diseño o de la implementación. Una **pregunta abierta** es algo que aún no se sabe. No mezclar.
- Fechas: tomadas del commit que introdujo la decisión, o de la fecha que el propio spec registra en su historial.

## 1. Decisiones

| # | Decisión | Por qué | Fecha | Alternativas descartadas | Estado |
|---|---|---|---|---|---|
| D1 | Supabase como único backend (Auth + Postgres + Edge Functions + Realtime) | Cero infra propia que mantener para un proyecto de un solo dev; todo el stack de datos en una pieza | 2026-05-13 | Backend Node propio + Postgres gestionado (infra y despliegue a cargo del dev); Firebase (sin SQL rico ni pgvector) | ✅ Firme — caduca si se necesita un job de más de 150s o un WebSocket propio para TTS streaming (V2) |
| D2 | pgvector dentro del mismo Postgres para el RAG de `user_facts` | Retrieval en el mismo motor donde ya viven las sesiones: joins directos, sin sincronizar dos fuentes | 2026-05-13 | Pinecone / Qdrant (otra pieza, otro costo, sincronización manual con Postgres) | ✅ Firme — revisar si un usuario supera ~50k `user_facts`: el índice IVFFlat `lists=100` está dimensionado para menos de esa cifra |
| D3 | Auth por Magic Link de Supabase (email) | Cero SDK extra y multi-usuario listo para abrir el repo; sin gestión de contraseñas | 2026-05-13 | OAuth social (SDK y config por proveedor); usuario+contraseña (obliga a gestionar credenciales y recuperación) | ✅ Firme |
| D4 | El audio nunca se persiste: solo el texto transcripto | Privacidad (la voz es el dato más sensible del producto) + costo de storage cero | 2026-05-13 | Guardar clips en Supabase Storage para re-análisis posterior | ✅ Firme — caduca si se implementa re-scoring de pronunciación sobre sesiones pasadas, que exigiría el audio original |
| D5 | RLS activo en todas las tablas con el patrón `(SELECT auth.uid())` + `TO authenticated`; la vista materializada se expone solo vía función `SECURITY DEFINER` | El cliente usa la anon key: el RLS es el único escudo entre un usuario y los datos de otro. El subquery cachea el `auth.uid()` (evita re-evaluación fila a fila) y las vistas materializadas no soportan RLS nativo | 2026-05-13 | `auth.uid()` directo en la política (se re-evalúa por fila); políticas sin `TO authenticated` (se evalúan también para `anon`); exponer la mat. view con `GRANT SELECT` (filtraría filas ajenas) | ✅ Firme |
| D6 | Todo el LLM pasa por el proxy OpenCode (plan Go) en vez de APIs pagas directas | El plan ya está pagado por otras razones: el costo marginal de LLM es cero y deja el gasto mensual en ~$1.41 (STT + TTS + Azure) | 2026-05-23 | GPT-4o / GPT-4o-mini directo a OpenAI (~$3.20/mes extra por el mismo volumen) | ✅ Firme — caduca si el plan Go se satura: el fallback es cambiar `LLM_ENDPOINT` y `LLM_MODEL`, sin tocar código |
| D7 | DeepSeek V4 **Flash** para la conversación en vivo, DeepSeek V4 **Pro** para todo lo asíncrono (feedback, judge, extract) | La conversación es latencia-crítica y Flash entrega tokens 3-4× más rápido a costa de ~5% de razonamiento, imperceptible en tutoría B1-C1. Los jobs asíncronos no los espera nadie: ahí conviene gastar 3-6s en razonar bien | 2026-05-23 | Pro para todo (mata la latencia del voice loop); Flash para todo (peor JSON estructurado en feedback); GPT-4o-mini (cuesta por llamada, ver D6) | ✅ Firme — caduca si el alemán B2 rinde mal: swap a Qwen3.6 Plus solo para `lang === 'de'` |
| D8 | El modelo de feedback es DeepSeek V4 Pro y **no** Claude Sonnet 4.5, que era la elección original | El plan de Claude se reserva para crafting y coding del proyecto, no como API de runtime | 2026-05-23 | Claude Sonnet 4.5 vía API directa (+$0.005-0.01 por sesión) | ✅ Firme — caduca si la precisión del feedback baja del 90% en validación manual |
| D9 | LanguageTool corre **en paralelo** al LLM de feedback como segundo opinador rule-based, no autoritativo | Atrapa grammar puramente sintáctica que el LLM pasa por alto; al ser paralelo, la latencia total es `max(LLM, LT)` ≈ la del LLM solo. En colisión de span gana el LLM porque su justificación es más rica | 2026-05-23 | Cascada LLM→LT (suma latencias); LT como autoridad (marca falsos positivos sin contexto conversacional); no usarlo | ✅ Firme |
| D10 | Embeddings con `text-embedding-3-small` (1536d), tratado como **inmutable** en producción | Costo marginal (~$0.001/sesión) y dimensión soportada nativamente por pgvector con IVFFlat. Cambiar el modelo obliga a reindexar *todos* los `user_facts` históricos | 2026-05-23 | `text-embedding-3-large` (3072d: duplica costo y storage sin ganancia perceptible en retrieval personal); embeddings del pool OpenCode (mismo problema de reindexado) | ✅ Firme — solo cambia con una migración de reindexado planificada |
| D11 | STT con Groq Whisper Large v3 Turbo | Whisper open-source sobre LPU de Groq: ~300ms y ~$0.04/h de audio, 5-10× más rápido que la API oficial a menor precio | 2026-05-13 | OpenAI Whisper API (misma interfaz, más lenta y más cara) — queda como fallback si Groq cae | ✅ Firme |
| D12 | TTS con OpenAI `tts-1` (`nova` EN / `onyx` DE) en el MVP; ElevenLabs Turbo diferido a V2 | `tts-1` es suficientemente bueno a ~$0.90/mes. ElevenLabs baja la latencia percibida de ~1.7s a ~0.9s pero cuesta ~$13.20/mes al mismo volumen: sin queja real de lentitud, no se justifica | 2026-05-13 | ElevenLabs Turbo desde el MVP (20× el costo por carácter) | ✅ Firme — caduca cuando la latencia percibida sea el bottleneck medido (ver Q5) |
| D13 | Pronunciación con Azure Speech Pronunciation Assessment, servicio dedicado y no un LLM | Devuelve scoring fonético granular (accuracy, fluency, completeness, prosody); ningún LLM general produce eso | 2026-05-13 | Speechace API (caro, calidad similar); WhisperX + alignment (complejo, peor accuracy); un LLM "escuchando" el audio (no hay scoring fonético real) | ✅ Firme |
| D14 | El feedback se genera **solo al cerrar la sesión**, nunca en tiempo real | Mantiene la conversación fluida (zero-friction) y permite al LLM ver el hilo completo: no marca como error algo que el usuario corrigió dos turnos después | 2026-05-13 | Corrección en vivo turno a turno (rompe el flujo conversacional y multiplica llamadas) | ✅ Firme |
| D15 | El análisis per-turn (`analyze-turn`) sí corre **durante** la sesión, en background, y el job de cierre solo agrega lo pre-computado | Baja el loader post-sesión de 15-20s a 2-3s. No contradice D14: nada se le muestra al usuario hasta el cierre | 2026-05-24 | Hacer todo el análisis al cerrar (loader de 15-20s) | ✅ Firme |
| D16 | Ante fallo de parseo del JSON de feedback: 2 reintentos (uno con prompt más estricto, otro con campos mínimos) y luego `feedback_status='failed'` + popup con HITL opcional | Acota el costo del reintento y deja al usuario una salida en vez de perder la sesión en silencio | 2026-05-13 | Reintentar indefinidamente (costo sin techo); fallar al primer intento (desperdicia sesiones recuperables) | ✅ Firme |
| D17 | El usuario puede rechazar una anotación: baja `weight`, sube `user_rejections`, y el item se archiva solo si `user_rejections >= 2` **y** `weight <= 0` | El LLM comete errores de evaluación; sin escape hatch, la librería de errores se contamina y el SRS entrena ruido. Exigir las dos condiciones evita archivar por un rechazo aislado | 2026-05-13 | Archivar al primer rechazo (un tap accidental borra un error real); no permitir rechazo (el ruido se acumula) | ✅ Firme |
| D18 | Graduación de un `tracked_item` por criterio híbrido: `weight <= 0` **y** `srs_state.interval >= 14d`, más confirmación manual del usuario (Opción C) | El weight solo mide errores recientes y el intervalo solo mide retención: juntos son evidencia de dominio. La confirmación manual evita que la app decida por el usuario | 2026-05-13 | Graduación automática solo por `weight` (falsos positivos por rechazos); solo manual (nunca se ejecuta); solo por intervalo (gradúa items que se siguen fallando) | ✅ Firme (el criterio sigue vigente; su **destino** lo redefine D19) |
| D19 | Al graduarse, el item se **promueve a `vocabulary_catalog`** (`source='promoted_from_tracked'`) y luego se archiva; ya no se archiva a secas | El archivo perdía la información: el usuario no tenía dónde ver lo que ya domina. El catálogo convierte la graduación en un registro permanente | 2026-05-25 | Archivar sin registro (comportamiento anterior, pierde el histórico de vocabulario); mantener el item activo tras graduar (satura el SRS) | ✅ Firme — supersede el destino definido en D18 |
| D20 | `vocabulary_catalog` es una tabla aparte de `tracked_items`, con entradas **permanentes** y `definition`/`example` **no editables** por el usuario (solo `user_note`) | Son dos ejes distintos: `tracked_items` mide rendimiento actual y muta; el catálogo refleja vocabulario activo en el tiempo y no debe mutar. Bloquear la edición de la definición evita drift de la base generada por LLM | 2026-05-25 | Reusar `tracked_items` con un flag `mastered` (mezcla dos ciclos de vida incompatibles); permitir editar la definición (drift); permitir borrar entradas (rompe el histórico) | ✅ Firme |
| D21 | `catalog_min_level` se **deriva** del nivel declarado en onboarding (un nivel por debajo), no se infiere del rendimiento | La inferencia automática tiene poca precisión y produce mala UX (sugerencias absurdas). El nivel declarado ya existe en `user_settings.languages_config` | 2026-05-25 | Inferir el nivel desde métricas de sesión (poca precisión); pedir el floor explícitamente en un paso extra de onboarding (fricción) | ✅ Firme — el usuario puede ajustarlo a mano desde settings |
| D22 | Guided Practice es un **tercer modo propio**, no una opción dentro de Free Chat ni de Roleplay | En conversación libre los chips romperían el flujo; en roleplay romperían el personaje. El modo declara explícitamente la intención de forzarse a producir X, y la UI se diseña alrededor de esa intención | 2026-05-25 | Toggle de chips dentro de Free Chat; chips dentro de Roleplay | ✅ Firme |
| D23 | Los chips no tienen enforcement duro: re-prompt suave, cooldown de 2 turnos si el usuario los ignora dos veces seguidas, y los 2 primeros turnos de cada sesión nunca llevan chips | El objetivo es producción activa, no obediencia: bloquear al usuario mataría el zero-friction. El warm-up forzado evita saturar el saludo | 2026-05-25 | Exigir el uso del chip para avanzar (bloquea al usuario); chips en todos los turnos incluido el saludo (sensación de acoso) | ✅ Firme |
| D24 | El orden de los chips es SRS-first por defecto (tracked items en slots 1-2, luego corpus B2, luego el contextual del LLM) | Latencia mínima y consistencia de UX: el orden se arma sin esperar al LLM | 2026-05-25 | Dejar que el LLM ordene por relevancia contextual | 🟡 Provisional — se revisa si se mide que el orden del LLM no añade >200ms de latencia perceptible (ver Q12) |
| D25 | `b2_expressions_corpus` es una tabla **global** (no por usuario), curada a mano y versionada como migración SQL; semilla ~150 expresiones de Oxford Learner's + Cambridge; solo EN en el MVP | La calidad del corpus es el producto: una ingesta automática mete ruido y problemas de licencia. Global porque "show up" es la misma expresión para todos | 2026-05-25 | Ingesta automática recurrente por scraping; corpus por usuario (duplica datos idénticos) | ✅ Firme — el crecimiento esperado es +20-30 expresiones por categoría débil detectada |
| D26 | Navegación principal por **swipe horizontal**, sin tab bar, y **cada swipe tiene un botón fallback** visible | La tab bar rompe el zero-friction y se siente antigua; el fallback mantiene la descubribilidad y permite desactivar cualquiera de los dos caminos sin perder la función | 2026-05-13 | Tab bar inferior; solo swipe sin fallback (invisible para usuarios nuevos) | ✅ Firme |
| D27 | `HorizontalNav` propio con membrana SVG elástica (Reanimated + Gesture Handler + react-native-svg) reemplaza a `react-native-pager-view` | El swipe deja de ser navegación y pasa a ser transición de contexto mental (free talk → roleplay): eso exige deformar el borde, cosa que un pager no permite. La entidad animada es la geometría, no el botón | 2026-05-24 | `react-native-pager-view` (no deforma el borde); Skia desde el inicio (potente pero prematuro: se descarta hasta que el SVG no alcance) | ✅ Firme — caduca si el path SVG no sostiene 60fps en gama baja: migrar a `@shopify/react-native-skia` |
| D28 | Drag continuo con umbral **invisible** (completa si `translationX > 45%` del ancho **o** `velocityX > 1200`), no hold-to-unlock | Es cómo se comporta iOS y cómo espera el usuario: la física decide, no un estado "armado". Un gate de confirmación se siente a slider mecánico y mata la sensación líquida | 2026-05-24 | Hold → unlock → release (interacción gateada); threshold fijo solo por distancia (ignora la intención del gesto rápido) | ✅ Firme |
| D29 | El micrófono es **tap-toggle** (no press-and-hold) y el audio de menos de 2s se descarta en silencio, sin llamar a ninguna API | Press-and-hold no funciona con el teléfono en el bolsillo ni con audífonos. El descarte silencioso evita costo y ruido por taps accidentales | 2026-05-13 | Press-and-hold; hold-to-start de 1.5s (evaluado y descartado: contradice el tap-toggle de los turnos y agrega fricción acumulativa); procesar todo audio (paga APIs por taps accidentales) | ✅ Firme |
| D30 | La despedida se detecta con **function calling** (`end_conversation` con `confidence`, `farewell_phrase`, `reasoning`), no con sentinel tokens en el prompt | Mismo round-trip (cero latencia extra), JSON con schema validado, `confidence` numérico explícito y API estandarizada entre proveedores | 2026-05-24 | Sentinel token en el texto de respuesta (frágil, se filtra al usuario); llamada extra a un clasificador (suma latencia y costo) | ✅ Firme — el botón "End conversation" siempre prevalece sobre el LLM |
| D31 | Focus mode con **fade progresivo en 3 niveles** (normal → parcial al primer tap → completo tras la primera respuesta persistida) | Entrar en focus completo desde el primer tap obligaría a salir bruscamente cuando el audio <2s se descarta (D29). El fade evita la sensación de "ventana muerta" | 2026-05-24 | Focus completo inmediato al tap; sin focus mode (gestos accidentales durante la conversación) | ✅ Firme |
| D32 | Dark mode por defecto; fondo `#0C0D0B` (negro neutro cálido); glass en 3 tiers con **máximo 2 por pantalla** y nunca el mismo tier apilado | El glass es el único agente de "vida" del sistema: apilar tiers iguales lo aplana y produce ruido visual. El `#1A1F18` anterior tenía sesgo verde-bosque incompatible con un glass neutro | 2026-05-24 | `#1A1F18` (sesgo verde); liquid glass 3D (inconsistente con cards planas); un solo tier de glass (sin jerarquía) | ✅ Firme |
| D33 | Escala tipográfica cerrada de 6 tokens (`display`, `logo`, `nav`, `body`, `caption`, `fine`) sobre 3 familias | Sin escala cerrada aparecen tamaños ad-hoc por pantalla y el sistema deja de leerse como uno solo | 2026-05-24 | Tamaños libres por componente (el anti-pattern que se venía corrigiendo en `theme/index.ts`) | ✅ Firme |
| D34 | En roleplay la IA adopta el rol **implícito en el texto del escenario**, sin nombre propio, y lo sostiene fijo hasta el cierre narrativo (~5 min, sin corte forzado) | El escenario ya contiene el personaje ("the clerk is uncooperative"): pedirlo aparte sería fricción de setup. El corte forzado rompería la escena a media frase | 2026-05-13 | Personaje con nombre y ficha aparte (setup más largo); corte duro a los 5 min; IA sin personaje en roleplay (indistinguible del modo libre) | ✅ Firme |
| D35 | Export a Obsidian por `PUT` a la GitHub REST API, con **fallback automático a Pull Request** si el PUT falla | Mantiene el vault sincronizado sin pagar Obsidian Sync; el PR cubre conflicto, permisos insuficientes o branch protegido sin perder la nota | 2026-05-13 | Obsidian Sync (de pago); servidor de sync propio (infra); fallar y descartar la nota | ✅ Firme |
| D36 | Validación de facts en dos etapas: retrieval con pgvector (distancia < 0.45) y **luego** un LLM judge que clasifica en IDEMPOTENT / REFINES / CONTRADICTS / CONTEXT_DEPENDENT / UNRELATED | Los embeddings no detectan contradicción: "me gusta X" y "odio X" son vecinos en el espacio vectorial. La lógica semántica tiene que vivir en el LLM. El umbral 0.45 (más permisivo que el típico 0.15) es deliberado: las contradicciones suelen estar a distancia media | 2026-05-24 | Deduplicar solo por similitud vectorial (no distingue refinamiento de contradicción); mandar todos los facts al LLM sin retrieval previo (costo y contexto) | ✅ Firme |
| D37 | `CONTEXT_DEPENDENT` **nunca sobreescribe**: marca el fact con `needs_clarification=true` y la IA pide la aclaración en conversación cuando el tema se cruza | "Me gusta la ensalada" + "no me gustan las verduras" puede no ser contradicción. Una IA que recuerda **y** aclara es el diferenciador del producto | 2026-05-24 | Sobreescribir el fact viejo (pierde matiz y "olvida" mal); descartar el nuevo (la memoria se congela) | ✅ Firme |
| D38 | `extract-facts` se dispara **cada 3 turnos** del usuario durante la sesión más una pasada final obligatoria al cerrar | Cada-6 pierde detalle en conversaciones cortas, cada-1 satura. La pasada final cubre las sesiones de menos de 3 turnos | 2026-05-24 | Cada turno (satura y encarece); solo al cerrar (pierde granularidad y alarga el cierre) | ✅ Firme — el número es config app-wide, ajustable sin redeploy |
